## 一、项目简介

「麦麦食历」不是一个点餐助手，而是一个**周菜单决策工具**。

用户只需回答一个问题——"这周什么状态？"——系统基于麦当劳官方 MCP 数据（餐品、营养、价格、优惠、活动），生成一份 **7 天 × 每日餐次的完整菜单**，满足热量、营养、预算、口味轮换等多重约束。用户可以随时"同价位调换 / 同热量调换 / 直接删减"，也可以在某一天临时切换状态。

**它解决的不是"这一顿吃什么"，而是"这一周不用再想"。**

## 二、要解决的问题

### 决策疲劳：每天两次的无形成本

对于学生、上班族、自由职业者，"中午吃什么、晚上吃什么"是每天发生两次、无法回避、却消耗真实思考能量的任务。叠加健身人群的额外约束（今天练力量要不要多碳水、减脂期热量怎么控），一次决策的成本更高。

### 市面方案的缺口

现有的"热量计算器"和"点餐助手"都停留在**单餐**层面：帮你算这一顿、推荐这一个。但真实需求是**周期性**的——没有人想连续七天做七次同样的决策。

### 麦当劳产品矩阵里的空白

麦当劳有完整的"周节奏营销"（周一麦麦省、周六麦金喜、周末麦麦惊喜），但从来没有一款以"周"为形态的产品。「麦麦食历」填补的正是这个空白。

## 三、目标用户

| 用户 | 核心诉求 |
|---|---|
| 大学生（含健身人群） | 预算有限 + 减脂增肌需求 + 食堂吃腻了 |
| 上班族 / 自由职业者 | 没时间想、午饭选择少、希望省心省钱 |
| 生病中的任何人 | 发烧、肠胃不适时，连打开 App 想吃什么都很痛苦 |

## 四、核心功能：四张状态卡，一个约束引擎

> **V1 设计，V2 已取消。** V2 不再用"状态卡/人群标签"，改为情境化输入（今天怎么样 / 想吃点什么感觉的 / 有多饿 + 可选预算与忌口），且**病号模式已删除**。详见 `docs/PRD_V2.md` §4。

所有模式共用同一个菜单求解引擎，区别只是**换一组约束参数**。

| 模式 | 解决的问题 | 约束模板 |
|---|---|---|
| **日常**（默认） | 今天不想想 | 均衡热量 + 价格带 + 轮换不重样 |
| **省钱** | 月底了，预算紧张 | 预算上限 + 券与促销组合最优价 |
| **燃脂** | 健身期，热量与蛋白要算清 | 热量缺口 / 盈余 + 蛋白下限 |


### 功能明细

> 以下 5 条均为 **V1 设计，V2 未采用**（V2 功能范围见 `docs/PRD_V2.md` §7：单次开盒、三种差异化推荐、重开、离线演示）。

1. **一周菜单生成**：输入状态 → 输出 7 天菜单，每日标注热量、蛋白质、价格、营养合计与周预算总计。
2. **单品级调换**：任一条目可"同价位调换""同热量调换""直接删减"，实时重算当日与整周账单。
3. **轮换约束**：相邻日不重复、同一餐品一周出现次数上限，防止味蕾边际效应递减。
4. **状态临时切换**：一周菜单中某一天可单独切换状态。


## 五、创新点

> **以下为 V1 的创新点陈述，V2 已改为体验层创新**（三个角色、零输入可用、惊喜有边界、理由可追溯）。V1 中"周期决策托管"已降级，**病号模式已删除**。

1. **从"单餐推荐"升级为"周期决策托管"**：竞品都在解决"这一顿"，本项目解决"这一周"，填补麦当劳产品矩阵的周期形态空白。
2. **约束引擎统一架构**：四个模式不是四个功能模块，而是同一求解器的四组约束参数——工程上可扩展，产品上可生长（未来可增加"聚会日""犒赏日"等模板）。

4. **可调换而非全自动**：把最终控制权留给用户，算法只负责把"选项空间"收敛到可决策的规模。

## 六、技术架构

### 作品形态

WorkBuddy Skill（智能体技能包）+ 离线演示脚本（无需 Token 即可跑通全流程，便于评审与用户体验）。

### 数据来源：全部来自麦当劳官方 MCP

| 用途 | MCP Tool |
|---|---|
| 营养数据（热量 / 蛋白 / 脂肪 / 钠） | `list-nutrition-foods` |
| 套餐与单品查询 | `query-meals` / `query-meal-detail` |
| 价格核验（券后实付价） | `calculate-price` |
| 可领优惠券 | `available-coupons` |
| 促销信息 | `query-promotions` |
| 当月活动日历 | `campaign-calendar` |
| 附近门店（可选） | `query-nearby-stores` |
| 个人历史偏好（可选） | `order-list` |

> **合规声明：本项目不抓取、不缓存任何非官方数据源。所有业务数据均在运行时通过 MCP 工具实时获取；工具未返回的字段一律标注"无法确认"，不以经验值替代。**

### 处理流程

```
用户状态选择
   ↓
约束模板实例化（热量区间 / 蛋白下限 / 脂肪钠上限 / 预算 / 轮换 / 禁忌）
   ↓
MCP 拉取候选餐品与营养、价格、优惠数据
   ↓
约束求解（候选集过滤 → 组合优化 → 轮换去重）
   ↓
7 天菜单 + 每日营养账单 + 周预算
   ↓
用户调换 / 删减 / 状态切换 → 局部重算
```

## 七、使用示例（V1 设计稿；V2 主流程为单次开盒，见 `docs/PRD_V2.md` §5）

```
用户：帮我排这周怎么吃，月底了，预算一周 150 块。
麦麦：好，这周按【省钱模式】排。
     周一 午：1+1 随心配（约 ¥13.9）· 约 520 kcal · 蛋白 22g
     周一 晚：……
     ……
     本周合计：¥146.3 · 日均 4 顿之外无额外支出
     任意一条可直接说"换个同价位的"或"这道不吃"。
```

> V2 的实际交互是：说一句"今天汇报搞砸了，想吃点满足的，别超 35"，拿到「懂你 / 稳妥 / 惊喜」三个选择。

> 具体菜品与价格以 MCP 实时返回为准，示例仅示意交互形态。

# PRD_CHANGELOG — V1（周菜单）→ V2（选餐魔盒）

| 项 | 内容 |
|---|---|
| 对比基准 | `docs/PRD.md` v0.1（2026-10-19，10,509 字节，**未修改、未覆盖**） |
| 当前版本 | `docs/PRD_V2.md` **v2.1（减法版）** |
| 变更性质 | 产品方向重构 + 本轮减法收敛 |
| 一句话 | 从"帮你规划一周"改为"这一顿，给你三个不一样的答案"；并把营养、减脂、技术叙事全部移出主线 |

---

## 0. 为什么改

1. **V1 的主流程成本太高**：选状态 + 填 6 项档案，才换到一张 7 天菜单。但真实场景是"我现在就要点"。
2. **V1 的差异化站不住**：卖点是"周尺度 + 轮换"，但 MCP 只提供单餐级价格/营养，周尺度没有额外数据支撑。
3. **v2.0 又跑偏了**：三路数学评分、营养目标求解、三档随机、营养完整度上首屏——主线被技术细节冲淡，产品看起来像"套着魔盒包装的营养计算器"。
4. 因此 v2.1 做减法：**只保留"状态表达 → 三个差异化选择"这条主线**。

## 2. V1 → V2 逐项对照

### 2.1 一周菜单规划

| 项 | 内容 |
|---|---|
| 旧设计 | 主流程：选状态 → 生成 7 天 × N 餐菜单 |
| 新设计 | **降级为 P2**。V2 主流程是单次开盒；赛后若做，形态是"连续 7 次开盒 + 轮换"，不单独做周求解器 |
| 原因 | 单次决策是高频真实场景；周求解器需要全量营养映射 + 组合优化，5 天做不出可验收版本 |
| 开发影响 | 正面：候选从"组合空间"缩到"官方售卖单元"，工作量降一个量级 |
| 待确认 | 赛后是否真要做（不影响本轮） |

### 2.2 周/日营养账单

| 项 | 内容 |
|---|---|
| 旧设计 | 单餐 → 单日 → 整周三級汇总 |
| 新设计 | **删除**。只保留单张卡片的一行"营养参考（如可得）" |
| 原因 | 没有周菜单就没有周账单；多级汇总会把 84.8% 的匹配误差层层放大 |
| 开发影响 | 少一个汇总模块，少一堆精度争论 |

### 2.3 轮换硬约束 R1/R2

| 项 | 内容 |
|---|---|
| 旧设计 | R1 相邻两天不重复；R2 同品一周 ≤2 次 |
| 新设计 | **延后 P2**；单次场景用 D1（三方案主商品互异）承接"别给我三个一样的" |
| 原因 | 单次没有日期概念，但用户心理是同一条 |
| 开发影响 | 不实现日期逻辑，只做方案间去重 |

### 2.4 四种状态卡（日常/省钱/燃脂/病号）

| 项 | 内容 |
|---|---|
| 旧设计 | 四张卡，各一套约束参数 |
| 新设计 | **整体取消**。改为三类正交输入：**状态**（累了/心情不错/低落/想奖励/简单解决）、**感觉**（满足/热乎/清爽/甜一点/想尝鲜）、**份量**（垫一下/正常/很饿），外加可选的预算与忌口 |
| 原因 | ① 状态卡是"人群假设"，用户未必认同被归类；② "燃脂"暗示减脂承诺；③ 用户真正能表达的是"我现在的状态和想吃的感觉"，不是"我属于哪类人" |
| 开发影响 | 输入层重构；推荐层只需一张"状态→倾向"规则表，不需要四套模板 |
| 待确认 | 无（已定） |

### 2.5 病号模式

旧版疾病导向模式已移除。V2 不提供病号入口、疾病饮食或治疗性饮食建议，也不再保留相关待确认项。

### 2.6 换餐与重新生成

| 项 | 内容 |
|---|---|
| 旧设计 | 同价位换（±15%）/ 同热量换（±10%）/ 直接删减 |
| 新设计 | **重开魔盒 = P0**（换 seed，且不与上一轮重复）；**单项换餐 = P1**；"删减"删除 |
| 原因 | 单次场景下用户要的是"再给我一组"，不是"在这组里微调"；"删减"在套餐语境下语义不清 |
| 开发影响 | P0 只需换 seed 复用候选池 |

### 2.7 「帮我带」卡片

| 项 | 内容 |
|---|---|
| 旧设计 | 病号模式专用输出 |
| 新设计 | 泛化为任意方案可生成（"帮我带一份：xxx，¥xx"）→ **P1** |
| 原因 | 成本极低、是自然传播路径；但不属于体验闭环，P0 不占位 |
| 待确认 | 文本是否带价格（建议带，并注明"以门店为准"） |

### 2.8 营养与预算约束

| 项 | 内容 |
|---|---|
| 旧设计 | 四个模式各把营养当硬约束（如燃脂 350–550 kcal、蛋白 ≥20g）；预算日均 ≤¥25 |
| 新设计 | **预算 = 硬约束，但用户填了才生效，默认不限**（不假定消费能力）；**营养完全不参与推荐**，只在详情行显示 |
| 原因 | ① 营养阈值是 V1 替用户定的，无依据；② 实测匹配 84.8%，做硬约束会误杀候选；③ 预算来自 `calculate-price` 实数，可靠 |
| 开发影响 | 推荐层零营养逻辑；数据层保留营养字段作未来扩展，但 P0 不要求全量映射（只需对被推荐的 3 个按需取） |

### 2.9 旧验收标准

| 项 | 内容 |
|---|---|
| 旧设计 | AC1 10 秒出 7 天菜单 / AC2 R1 违反 0 / AC3 95%+ 营养 / AC4 调换重算 0 误差 / AC5 病号阈值 / AC6 离线 / AC7 示例不造假 |
| 新设计 | **全部重写为 AC1–AC9**：低成本启动、输入影响输出、三方案真实差异、随机真实性、硬约束、价格可追溯、缺失诚实、离线可跑、讲得清 |
| 原因 | 旧 AC 绑定周菜单/调换/病号，失去对象；且 AC3 的"95%+"是不可达估算值 |
| 待确认 | 无 |

### 2.10 离线演示

| 项 | 内容 |
|---|---|
| 旧设计 | `demo_offline.py` 内置"脱敏样例数据" |
| 新设计 | **保留 P0 并升级**：用**真实调用快照**（含抓取时间），卡片标注"快照数据（非实时）"，禁止手编价格/菜品 |
| 原因 | 手编样例有"编造数据"风险；真实快照既离线可跑又可追溯 |
| 开发影响 | 数据层需支持"在线拉取 → 落盘 → 离线读取"，两种模式输出结构一致 |

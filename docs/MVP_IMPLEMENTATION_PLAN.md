## 0. 这次只做一件事

**让一个人打开它，3 次点击内拿到 3 个不一样的选择，并且能说清为什么。**

其余一律靠后。营养不算、周菜单不做、档位不做、账号不做。

## 2. 模块（6 个文件，不多）

```
mcd_box/
├── adapter.py     # 唯一出网点：MCP 调用 + 缓存 + 快照读取
├── candidates.py  # 候选构建：菜单 → 标准结构（带价格、分类、tags、子项）
├── recommend.py   # 硬过滤 + 三条选择规则 + D1–D3 校验 + 随机采样
├── entry.py       # 三种入口 → 统一 Query（含 L0 文本解析与回显文案）
```

外加两个脚本：`scripts/build_snapshot.py`（抓一次真实数据存快照）、`scripts/demo_offline.py`（读快照跑 3 个用例）。

> **明确不建**：`nutrition.py`（营养只在 render 里按需查 3 条）、`scoring.py`（没有评分体系了）、`solver.py`（规则就在 `recommend.py` 里，不需要"求解器"这个名字）。

## 3. 任务顺序（严格按依赖，不按重要性）

### 步骤 1 · 验证真实菜单与价格链路（最优先，Day 1 上午）

| 做什么 | 产出 | 验收 |
|---|---|---|
| 用 `probe_mcp.py` 复用 `McpClient`，跑通 `query-meals` → `query-meal-detail` → `calculate-price` | `scripts/verify_chain.py` + 一次真实打印 | 能看到：品数、分类数、价格区间、几个真实餐品的名称+价格（分与元对照） |
| 统计目标门店（3350112）实际品数与价格分布 | 一个数字表 | 品数已知；价格中位数已知（后面"稳妥款"规则要用） |
| 采样看 `tags` 里到底有哪些词 | tag 频次表 | 知道"上新/限定/联名"是否真存在，决定惊喜款规则 |

**卡点判定（已通过，10-21）**：`query-meals` 0.4s 返回 102 个餐品且**自带名称与现价**，批量核价 4 次调用 1.2s 覆盖全部 → 冷启动约 6 次调用；原计划的「125 次详情」假设**不成立，已取消**。详情只在需要展开套餐子项时才调。

### 步骤 2 · 最小候选结构（Day 1 下午）

```python
@dataclass
class Cand:
    code: str
    name: str
    category: str
    tags: list[str]
    items: list[str]          # 默认子项名（isDefault=1）
    price_yuan: float | None
    has_set: bool             # 是否有 rounds（官方套餐）
    is_new: bool              # tags 含 上新/限定/联名
```

要求：
- `price_yuan` 缺失就是 `None`，**不许填 0 或估算**。
- 只保留"有价格"的候选进入推荐；无价格的单独留档，不进结果。
- 落盘 `data/cache/<storeCode>.json`，结构 = `{fetched_at, store, cands}`。

**验收**：`python -c` 能打印 `len(cands)`、价格中位数、带 `is_new` 的数量。

### 步骤 3 · 过滤 + 三条规则 + 差异化（Day 2）

| 子任务 | 说明 |
|---|---|
| `hard_filter()` | 预算（None 表示不限）、排除词（对 name + items + category 做子串匹配）、可售（天然满足） |
| `pick_understanding()` | 状态→倾向表命中 → 感觉标签命中数 → 搭配完整度；取第 1 |
| `pick_safe()` | 排除已选 → 优先 `has_set` → 价格 ≤ 中位数，按离中位数最近排序 → 排除 `is_new`；取第 1 |
| `pick_surprise()` | 排除已选 → 分类不同于懂你款 → `is_new` 优先 → 未提及品类 → 价格 ≥ 中位数；取第 1 |
| `ensure_diverse()` | D1 主商品互异（硬）、D2 分类不全同（软，附注）、D3 子项不完全相同（硬） |
| `random_box()` | `random.Random(seed).sample(pool, k)`，去重后凑 3 个主商品互异 |

**验收**：同一 query 连跑 10 次（固定 seed）结果一致；换状态后懂你款变化；三方案主商品两两不同。

### 步骤 4 · 三个入口（Day 2 晚 ~ Day 3 上午）

| 入口 | 实现 | 验收 |
|---|---|---|
| A 直觉输入 | 命令行交互：3 行选项 + 2 个可选（预算/忌口），回车即跳过 | 全跳过也能开盒 |
| B 自由表达 | L0 词典/正则抽 5 类槽位 → **打印回显** → 用户确认或改用标签 | 20 条测试句，能抽出预算/忌口/感觉三类即可；抽不到要明说 |
| C 随机 | 一个命令 `--random`，无任何参数 | 连点 20 次出现 ≥8 种组合 |

**L0 词表（先写这个，再写解析器）**：
- 预算：`(\d+)\s*元?以内|不超过\s*(\d+)|预算\s*(\d+)|(\d+)\s*块`
- 忌口：`不吃(.+)|不要(.+)|忌(.+)|别放(.+)`
- 感觉：满足/热乎/热一点/清爽/清淡/甜/尝鲜/新口味
- 状态：累/加班/心情不好/搞砸/奖励/随便/简单
- 份量：垫一下/不饿/很饿/饿死/正常

### 步骤 5 · 卡片与重开（Day 3）

卡片输出（CLI 纯文本，固定模板）：

```
【懂你款】 ¥26.90
龙焰鸡腿堡三件套 — 龙焰鸡腿堡 + 中薯条 + 可乐中杯
为什么是它：<由 input / 数据 / 规则 三段之一生成>
营养参考：约 620 kcal / 蛋白 27g     ← 可缺，缺则"营养数据暂无"
数据：门店 3350112 · 核价 2026-10-20 17:44 · 以门店实际为准
```

- 理由生成必须是**模板 + 变量**，变量只能来自：用户输入摘要、价格差、`is_new`、`has_set`、分类名。**不许自由发挥。**
- `--again` 换 seed，且排除上一轮三款（否则用户觉得没变化）。

**验收**：三张卡打印出来，30 秒内能读懂"吃什么、多少钱、为什么"。

### 步骤 6 · 快照 + 离线 demo（Day 3 晚 ~ Day 4 上午）

| 要求 | 标准 |
|---|---|
| `build_snapshot.py` | 抓一次真实数据 → `data/snapshot/<storeCode>.json`，带 `fetched_at`，**不自动覆盖** |
| `demo_offline.py` | 不读 Token、不发请求；`--case 1|2|3` 三个用例 |
| 三个用例 | ① 累了 + 想吃满足的 ② 一句话"汇报搞砸了，想吃满足的，别超 35" ③ 零输入随机 |
| 输出一致性 | 与在线模式字段完全相同，只有 `source="snapshot"` + 卡片尾行注明"快照数据（非实时）" |

**反作弊自查**：demo 脚本里不许出现任何写死的菜名/价格；评审搜到硬编码即失信。

### 步骤 7 · 测试（Day 4）

写成 `tests/test_rules.py`（纯标准库 `unittest`，不引 pytest）：

| 用例 | 断言 |
|---|---|
| T1 硬约束 | 30 组随机输入，所有结果 `price ≤ budget`（填了才判）、不含排除词 |
| T2 差异化 | 30 组，三方案 `code` 两两不同 = 100% |
| T3 输入影响 | 固定 seed，改状态/感觉/预算，≥80% 至少一款变化 |
| T4 随机 | 同 seed 两次结果一致；20 个 seed 出现 ≥8 种组合 |
| T5 缺失处理 | 构造一个无价格候选，断言它不出现在"稳妥款" |
| T6 离线一致 | 用快照跑，断言输出字段集合与在线一致 |

**与 PRD §13 的对应**：T1→AC5、T2→AC3、T3→AC2、T4→AC4、T5→AC7、T6→AC8；AC1（点击计数）、AC6（抽 5 个餐品核对价格）、AC9（找个没听过项目的人试讲）为人工验收，不写进自动化。

### 步骤 8 · 交付（Day 5）

README 改写为 V2（删掉四状态卡/病号/周菜单表述）、`MCP_INTEGRATION.md`（可直接由 `DATA_PROBE.md` 改写）、`CONTEST_DECLARATION.md`（官方原文）、`mcp-config.example.json`（占位符）、建仓库、推代码、Issue 报名。

**顺序不能反**：代码冻结后再写 README，否则文档写了功能却没实现，是比赛里最容易被扣分的点。

## 5. MCP 接入要求（照抄即可，别重新踩）

| 要求 | 做法 |
|---|---|
| 单点出网 | 只有 `adapter.py` 持有 token 与 HTTP 客户端 |
| Token | 环境变量 `YOUR_MCP_TOKEN`；没有就自动进 `offline` 模式并提示 |
| Bearer | 手工 HTTP 客户端必须 `Authorization: Bearer <token>`（裸 token 返回 403） |
| 门店 | `city + keyword` 必须同传；`beType=1`；不传 `beCode` |
| 价格 | 只信 `calculate-price` 的 `subtotal`（分→元），**不要从别处猜价** |
| 详情 | **不预取全量**；只在展示套餐子项时按 code 调，失败重试 1 次；失败只影响子项展示，不影响价格 |
| 营养 | 只对被选中的 3 个按需匹配（3 次），**不做 125 品全量映射** |
| 限流 | 单次开盒 ≤150 次调用；429 直接提示，不自动重试 |
| 缓存 | `data/cache/<storeCode>.json`，TTL 600s |
| 禁用 | `query-promotions`（仅团餐）、`create-order`/`cancel-order`、`delivery-*` |

## 6. 覆盖边界（必须如实写进 README）

不要等"125 个售卖单元都被完美计算"才让产品工作。第一版的实际覆盖就是：

| 项 | 第一版做到什么程度 |
|---|---|
| 门店 | 单店（默认烟台保利 3350112），**不做多店比较** |
| 场景 | 到店自取（`beType=1`），不做外送/得来速 |
| 候选 | 该门店接口返回的全部售卖单元（品数以实测为准） |
| 价格 | 全部候选都有真实核价（批量 1–2 次调用） |
| 名称/子项 | 全部候选都有详情（缓存） |
| 营养 | **只对被推荐的 3 个尝试匹配**；不完整就标"暂无" |
| 时段 | 不区分早/正餐（取到什么算什么，卡片显示时间） |
| 库存 | 不保证，卡片固定写"以门店实际为准" |

**这句话要写进 README**：本作品只覆盖单店到店场景，营养数据仅作辅助展示，推荐不依赖营养。

## 7. 高风险与应对

| # | 风险 | 信号 | 动作 |
|---|---|---|---|
| H1 | 详情调用太慢/限流 | 冷启动 >30s 或 429 | 两段式粗筛到 ~40 个；仍不行则用快照做半在线演示 |
| H2 | 三款看起来一样 | 自己看 5 组都觉得像 | 提高 D2 权重；惊喜款强制换分类；必要时牺牲"最优"换"不同" |
| H3 | 状态规则太弱，输入改了结果不变 | T3 用例失败 | 把状态规则的优先级提到最高（命中的先取），而不是只做同分排序 |
| H4 | 文本解析命中率低 | 20 句里 <10 句能抽到东西 | 只保留"预算 + 忌口"两类，其余引导标签 |
| H5 | 时间不够 | Day 3 结束还出不了三张卡 | 执行 §9 删减 |

## 8. 明确砍掉的东西（不进 MVP）

| 砍掉 | 原因 |
|---|---|
| 营养目标求解（热量上限/蛋白下限） | 数据支撑不足，且会把产品拉回减脂工具 |
| 营养全量映射（原 125 品） | 对体验没有贡献，只增加失败面；改为按被选中的 3 个按需查 |
| 三路数学评分 | 换成三条规则，更易解释 |
| 随机多档 | 多一层选择违背"随机"的意义 |
| Web UI | CLI + 截图足够评审看懂；做网页必然挤掉算法时间 |
| 周菜单 / 自组组合 / 订单历史 | 赛后 |

## 0. 一句话

> **今天吃什么，让魔盒替你少想一步。**
>
> 你可以告诉魔盒今天的状态、当下的心情和想吃的感觉，也可以什么都不说。  
> 魔盒从真实的麦当劳菜单里，找出三个各有理由的选择——少一点纠结，多一点发现。

**它解决的是"选不出来"，不是"吃得不对"。**

## 1. 产品定位与核心价值

### 1.1 定位

一个**单次用餐的选餐魔盒**：面对一整张菜单，用最低的启动成本，把选择空间收敛到 3 个有理由的答案。

**唯一主线是减少单次选餐的决策成本（决策疲劳）**——不是饮食管理、不是营养优化、不是减脂规划。判断一个功能该不该做，只问一句：它让用户少想一步了吗？

### 1.2 五条产品原则（本文件的宪法，后续设计不得违反）

1. **低成本启动**：不填档案、不注册、不答问卷。所有输入都可跳过，预算也可以不填。
2. **只理解用户主动表达的东西**：状态、心情、想吃的感觉，是用户说的，不是产品推断的。产品不判断用户的健康状况，也不替用户决定"应该吃什么"。
3. **主动缩小选择空间**：不把 100 多个餐品摊给用户看。产品的工作是"删掉大部分"，不是"全部展示"。
4. **三个有理由的答案，不是一个黑箱**：三个选择必须有实质区别，每个都能说清"为什么是它"。
5. **趣味来自过程，不来自术语**：好玩的是"说出此刻的自己 → 打开盒子 → 看到一个没想到但合理的选择"，不是算法名字。

### 1.3 核心价值

| 价值   | 具体表现                      |
| ---- | ------------------------- |
| 少想一步 | 3 次点击内出结果；不想点就直接开盒        |
| 不用比价 | 价格是真实核价结果，直接给到"这一份多少钱"    |
| 有发现感 | 第三个选项故意偏离你的习惯，但仍在你的限制内    |
| 不后悔  | 三个选项的差别写在明面上，选哪个都知道自己在选什么 |

### 1.4 与 V1 的关系

| 维度   | V1            | V2             |
| ---- | ------------- | -------------- |
| 时间尺度 | 一周 14 顿       | 这一顿            |
| 用户投入 | 选状态 + 填 6 项档案 | 0–3 次点击        |
| 输出   | 一张 7 天菜单      | 3 张卡片          |
| 核心   | 营养与轮换约束下的规划   | 状态表达 → 三个差异化选择 |
| 主线   | 饮食管理          | **决策疲劳**       |

> V1 是历史基线，保留在 `docs/PRD.md`，不再作为产品方向。

## 2. 目标用户与使用场景

| 用户              | 场景             | 他要的不是     |
| --------------- | -------------- | --------- |
| 学生（选择多、预算敏感）    | 下课后站在食堂门口，"吃啥" | 营养报告      |
| 上班族（午休 40 分钟）   | 电梯里 30 秒决定     | 一份 7 天计划  |
| 选择困难 / 今天状态不好的人 | "随便，但别让我更烦"    | 被分析心情     |
| 想换口味的人          | 板烧吃了三个月，想试点别的  | 被推荐"更健康"的 |

**明确不作为核心目标用户**：需要疾病饮食管理的人、需要营养治疗的人、需要减重方案的人。产品不服务这些需求，也不做相关承诺。

## 3. 痛点与创新点

### 3.1 痛点

| #  | 痛点                         | 依据                            |
| -- | -------------------------- | ----------------------------- |
| P1 | 选项过载：单店实测 102 个售卖单元、14 个分类 | 【实测】`query-meals`             |
| P2 | 价格口径混乱：现价 / 原价 / 会员优惠 / 券分散在多个字段，用户算不清这一单实付多少       | 【实测】`query-meals` 仅 code+tags |
| P3 | 每天两次重复决策，没人替你收窄范围          | 定性，不主张已量化                     |
| P4 | 新品/联名/限时散落在活动页，与菜单割裂       | 【实测】`campaign-calendar` 只有文案  |

### 3.2 创新点（体验层，不是技术层）

1. **三个角色，不是三个结果**：懂你 / 稳妥 / 惊喜，对应三种不同的"想要"。
2. **零输入可用**：不想说就不说，按钮一直在。
3. **惊喜有边界**：惊喜款只在你的限制内探索，不会推给你不吃的或超预算的。
4. **理由可追溯**：每句推荐理由都能对回"你说的话"或"接口给的数据"，没有心理分析，没有营养结论。

> 措辞红线：不说"更健康""帮你减脂""营养均衡""科学搭配"。

## 4. 三种开启方式

三个入口最终都变成同一个 `Query`，走同一套推荐规则。入口只决定"信息怎么来"。

### 4.1 入口 A：直觉输入（情境化选项，不是参数表）

**设计要求**：像聊天，不像表单。每行一句人话，选项是短语，不是滑块参数。**每一行都可以不选**，"开盒"按钮永远可点。

```
今天怎么样？
  [ 累了 ]  [ 心情不错 ]  [ 有点低落 ]  [ 想奖励自己 ]  [ 就想简单解决 ]

想吃点什么感觉的？
  [ 满足 ]  [ 热乎 ]  [ 清爽 ]  [ 甜一点 ]  [ 想尝鲜 ]
  （最多选 2 个）

有多饿？
  [ 垫一下 ]  [ 正常 ]  [ 很饿 ]

（可选）预算：  [ 不限 ]  ——  [ ¥15 —— ¥60 ]
（可选）不吃：  [ 牛肉 ] [ 辣 ] [ 冰的 ] [ 咖啡 ] [ 猪肉 ] [ 鱼 ]

                              [ 开 盒 ]
```

**关于预算的硬规定**：

- 默认 **不限**。
- 用户不填预算时，**不得假定其消费能力**，不得用"人均 35 元"之类的隐含假设排序。
- 填了才作为硬上限。

**"状态"如何影响推荐（防止变成心理分析）**：

状态只决定**往哪一类餐品倾斜**，用一张写死的产品规则表，不推断情绪、不推断营养：

| 用户选的状态 | 推荐倾向（产品规则，非心理学结论）                      |
| ------ | -------------------------------------- |
| 累了     | 优先"好拿好入口"：汉堡 / 卷 / 单手能吃的小食组合；避开需多人分的拼盘 |
| 心情不错   | 优先"有仪式感"：完整套餐，含甜点或饮品                   |
| 有点低落   | 优先"热乎、扎实"：热食 + 含主食；避开冰饮冷食              |
| 想奖励自己  | 优先"贵一点、特别一点"：高价位带 + 联名/限定/上新标记         |
| 就想简单解决 | 优先"步骤少"：单品或三件套；避开要选特调、要选口味的            |

> 这张表是**产品偏好设置**，不是对用户的判断。界面不出现"你心情不好所以需要热量"这类话。

**首屏控件上限**：3 行情境选项 + 2 个可选折叠（预算、忌口）。超出即违反原则 1。

### 4.2 入口 B：自由表达

示例：「今天汇报搞砸了，想吃点满足的，别超过 35 元。」

**能力边界（不建复杂 NLP）**：

| 级别 | 做法                                     | 覆盖          | 版本     |
| -- | -------------------------------------- | ----------- | ------ |
| L0 | 词典 + 正则，抽 5 类槽位：预算 / 忌口 / 感觉 / 状态 / 份量 | 高频表达够用，长句会漏 | **P0** |
| L1 | 模型只输出同 schema 的槽位 JSON，不参与排序           | 覆盖更好        | P1，可选  |

**必做的确认（解析回显）**：

```
我理解成这样，对吗？
  预算  ≤ ¥35        [改]
  不要  —            [改]
  想要  满足          [改]
  状态  有点低落      [改]
  份量  正常          [改]
        [就这样，开盒]   [改用标签选]
```

**三级降级**：

1. 抽到 ≥1 个槽位 → 回显 + 未抽到的用默认（不限），用户可直接开盒。
2. 一个都没抽到 → 直说"这句我没读懂具体限制"，原文留档，引导用标签。
3. L1 不可用 → 自动退回 L0，不报错。

> 原则：**理解不确定时，问，不要猜。** 宁可多一次确认，也不要推错。

### 4.3 入口 C：随机开启

**MVP 只做一档**：一个按钮，直接开盒。

- 候选池 = 通过硬约束（预算 / 忌口 / 该门店可售）的全部餐品。
- 采样 = 真随机，在池内均匀抽 3 个**主商品互异**的候选。
- 不按偏好排序。用户什么都没说，就没有偏好可排。
- 每次结果带 `seed`，可复现。

**多档（熟悉 / 惊喜 / 完全随机）→ P1**。理由：三档会多出一层选择，而"随机"的全部意义就是不用选；MVP 不做。

**随机 ≠ 不受约束**：预算、忌口、门店可售先过滤，再随机。抽到不合格的是不可能的。

### 4.4 个性化数据：只认这三类

| 类别                 | 是否可用于 MVP | 说明                                     |
| ------------------ | --------- | -------------------------------------- |
| ① 本次输入里的偏好         | ✅         | 状态、感觉、份量、预算、忌口                         |
| ② 产品自己记录并已实现读取的交互  | ⏸ P1      | 例如"选过哪些款"，存本地文件                        |
| ③ 接口验证可读的订单历史      | ❌ 当前不可用   | `order-list` 可调用但**当前账号返回空**（10-20 实测） |
| ④ 其他应用的搜索记录 / 浏览历史 | ❌ 永远不碰    | 无此能力，也不宣称有                             |

**没有历史偏好时，随机模式必须照常工作**（§4.3 的设计本身不依赖偏好）。

## 5. 完整使用流程

```
打开
 │
 ├─[A] 三行情境选项（可全跳过） ─┐
 ├─[B] 说一句话 → 回显确认 ──────┤
 └─[C] 直接开盒 ────────────────┤
                                 ↓
                     统一 Query（§9.1）
                                 ↓
            取数：该门店菜单 + 详情 + 核价（缓存/快照）
                                 ↓
                  硬约束过滤（预算/忌口/可售）
                                 ↓
        ┌──────────┬──────────┬──────────┐
      懂你款      稳妥款      惊喜款
        └──────────┴──────────┴──────────┘
                   差异化校验（主商品互异）
                                 ↓
                        3 张卡片
                                 ↓
        选它 │ 重开（换 seed） │ 改条件 │（P1：帮我带 / 换一个）
```

- 首次使用：默认取定位城市最近门店（实测烟台最近 599m 的「麦当劳烟台保利餐厅」），可改城市 + 关键词搜索。
- 二次使用：沿用上次门店，直接开盒。

## 6. 三种输出方案

### 6.1 三个角色

| 角色 | 名称      | 回答的问题      | 选择倾向            |
| -- | ------- | ---------- | --------------- |
| ①  | **懂你款** | 此刻最贴合我的    | 命中你说的状态与感觉      |
| ②  | **稳妥款** | 最不容易选错的    | 搭配完整、价格不冒进、不是新品 |
| ③  | **惊喜款** | 我没想过但可以试试的 | 跳出品类的、带限定/上新标记的 |

> 名称可继续打磨，**但三个角色不可合并**。

### 6.2 每张卡片有什么

```
【懂你款】  ¥26.9
龙焰鸡腿堡三件套
  龙焰鸡腿堡 + 中薯条 + 可乐中杯
为什么是它：你说"累了"，这套是单手能吃的汉堡套餐；
            中薯条 + 可乐搭配完整，不用再想加什么。
            价格比你的预算低 ¥8.1。
营养参考（如可得）：约 620 kcal / 蛋白 27g
数据：门店 3350112 · 价格 2026-10-20 17:44 核价 · 以门店实际为准

[ 就这个 ]   [ 换一个 ]   [ 重新开盒 ]
```

| 字段   | 要求                           | 缺失时              |
| ---- | ---------------------------- | ---------------- |
| 餐品组合 | 主商品 + 默认子项（套餐展开）             | —                |
| 价格   | 真实核价，元，两位小数                  | 显示"价格待确认"，不进合计比较 |
| 推荐理由 | 1–2 句，必须能对回输入或数据             | 不允许编             |
| 营养参考 | **可选，一行小字，放最后**              | 显示"营养数据暂无"，不影响推荐 |
| 数据提示 | storeCode + 核价时间 + "以门店实际为准" | —                |
| 操作   | 就这个 / 换一个（P1）/ 重新开盒          | —                |

**营养的位置（本轮明确）**：不进卡片主视觉、不进排序、不进筛选、不进验收指标。只在详情行出现，能算就算，算不出就说没有。

### 6.3 三种方案怎么做到"真的不一样"

只用三条规则，简单可测：

| 规则           | 内容                                           | 不满足时                              |
| ------------ | -------------------------------------------- | --------------------------------- |
| **D1 主商品互异** | 三个方案的 `productCode` 两两不同                     | 硬失败，重选                            |
| **D2 分类不全同** | 三个方案的主商品不能全属同一菜单分类                           | 尽量满足；候选不足时允许，并在卡片注明"三者同类，因可选范围有限" |
| **D3 结构不同**  | 不允许"同一餐品换三句理由"：主商品相同即违反 D1；主商品不同但子项完全一致，视为同款 | 硬失败                               |

**为什么不用综合评分**：三条规则就能保证"三个不同的东西"，而三套数学评分既难调、又难解释，还容易让用户觉得"这不都一样"。**能说清、能测、能改**比"看起来高级"重要。

### 6.4 一键操作

| 操作           | 价值              | 版本     |
| ------------ | --------------- | ------ |
| 重新开盒（换 seed） | 不满意就再来，最常用      | **P0** |
| 就这个（确认）      | 闭环              | **P0** |
| 改条件重来        | 回到输入            | **P0** |
| 换一个（同分类替换）   | 只换这一份，不推翻全部     | P1     |
| 帮我带（生成可复制文本） | 传播钩子，成本极低       | P1     |
| 替我决定         | 进一步降成本，但削弱"三选一" | P1     |

## 7. 功能范围

### P0 —— 不做完就没有作品（10 项）

| #  | 功能            | 说明                                               |
| -- | ------------- | ------------------------------------------------ |
| 1  | 真实菜单 + 可靠价格链路 | 单店；`query-meals`（含名称/现价/分类/tags）为主，`calculate-price` 只做校验与改单；带缓存与快照 |
| 2  | 直觉输入          | 3 行情境选项 + 预算/忌口（均可跳过）                            |
| 3  | 基础自由表达        | L0 规则解析 + 回显确认 + 三级降级                            |
| 4  | 三种差异化推荐       | 同一候选池 → 懂你/稳妥/惊喜，D1–D3 校验                        |
| 5  | 硬约束           | 预算（可空）+ 明确排除项 + 门店可售                             |
| 6  | 随机开启          | 单档，真随机采样，seed 可复现                                |
| 7  | 卡片            | 餐品、真实价格、推荐理由、数据提示；营养作可选详情                        |
| 8  | 重新开启          | 换 seed，且不与上一轮三款重复                                |
| 9  | 离线演示          | 真实数据快照，无 Token、无网络可跑                             |
| 10 | 核心规则测试        | 见 §13                                            |

### P1 —— 不影响核心创意成立

偏好记忆与历史行为个性化 · 多档随机 · 单项换餐 · 替我决定 · 更强的自由表达（L1）· 活动/上新信息接入 · 帮我带文本。

### P2 —— 赛后

一周菜单 · 自组组合（主商品 + 加购）· 历史订单个性化（待数据能力验证）· 更丰富的个性化推荐。  
**营养目标求解（热量上限/蛋白下限）不在 P0/P1，列 P2 且不承诺。**

## 8. 硬约束与软偏好

### 8.1 硬约束（违反即不合格，绝不放宽凑数）

| #  | 硬约束  | 规则                                                                                 |
| -- | ---- | ---------------------------------------------------------------------------------- |
| H1 | 预算   | **用户填了才生效**。`total <= budget`，价格取 `calculate-price` 的 `subtotal`（分→元）。不填 = 无上限，不假定 |
| H2 | 排除项  | 对商品名 + 子项名 + 分类做关键词排除（如"牛肉""辣""冰的"）                                                |
| H3 | 门店可售 | 候选必须来自该 `storeCode` 的 `query-meals` 返回                                             |
| H4 | 不伪造  | 价格/营养缺失一律标"待确认/暂无"，不推算、不用经验值                                                       |

### 8.2 软偏好

| 软偏好                              | 影响谁                       |
| -------------------------------- | ------------------------- |
| 状态（累了 / 心情不错 / 低落 / 奖励自己 / 简单解决） | 懂你款（按 §4.1 规则表）           |
| 想吃的感觉（满足 / 热乎 / 清爽 / 甜一点 / 想尝鲜）  | 懂你款；"想尝鲜"同时加权惊喜款          |
| 份量（垫一下 / 正常 / 很饿）                | 懂你款与稳妥款的价格带/搭配完整度         |
| 预算（即使不是硬上限）                      | 稳妥款优先"预算占用不高"的            |
| 什么都不选                            | 三款退化为：人气款 / 套餐完整款 / 限定上新款 |

### 8.3 忌口与过敏的诚实边界（红线）

- 我们**没有成分表**，只有名称和（部分）营养汇总。
- 忌口只能做**名称/分类关键词排除**，不是成分级排除。
- 卡片固定提示：**"忌口按名称匹配，不含成分与交叉接触信息，过敏请向门店核实。"**
- **绝不承诺"绝对安全/无过敏原"**，不出现"无麸质""低敏"等表述。

## 9. 推荐逻辑（MVP）

设计目标：**规则能说清、结果能复现、输入能影响输出**。不追求数学优雅。

### 9.1 输入 Query

```json
{
  "entry": "intuition | text | random",
  "store": {"storeCode": "3350112", "storeName": "麦当劳烟台保利餐厅", "beType": 1},
  "budget_yuan": null,
  "exclude": ["牛肉"],
  "state": "累了",
  "feel": ["满足"],
  "size": "normal",
  "seed": 1732456789012
}
```

### 9.2 流程（五步）

```
① 取候选：query-meals → 该门店餐品目录（`data.meals`：name + currentPrice + image）
         + 分类与 tags（`categories[].meals[]`），按 code 去重
② 补组合：仅当需要展示套餐子项时调 query-meal-detail（**不必对全量餐品调用**）
③ 硬过滤：预算（若填）→ 排除词 → 丢弃无价格的候选
④ 分三桶（规则，见 9.3）
⑤ 差异化校验（D1–D3），不足则按 9.5 降级
```

> 实测修正（10-21）：`query-meals` **自带名称与价格**，不需要为拿名称而全量拉详情。原先假设的"125 次详情调用"只在需要子项组合时发生，冷启动成本大幅下降。

**候选只用官方售卖单元**（套餐/单品本身），不做自组组合。理由：售卖单元天然可下单、有价格、有搭配，自组会让候选与核价成本同时爆炸。

### 9.3 三条选择规则（不是三套评分）

**懂你款**

1. 按"状态 → 倾向表"（§4.1）给候选打**是否命中**（0/1）。
2. 命中的里面，按"感觉标签命中数"排序。
3. 同分优先"搭配完整"（有主食 + 有饮品/小食的套餐）。
4. 取第 1 名。
5. **用户什么都没选时**：退化为"人气款"——优先带"人气/热卖"标记的，其次搭配完整的套餐。

**稳妥款**

1. 排除懂你款已选的主商品。
2. 优先"搭配完整"的官方套餐（有 rounds、子项齐全）。
3. 在剩余候选里，取**价格处于本次候选池中位数以下**的，按"离中位数最近"排序（不是最便宜——最便宜的往往是单品，不顶饱）。
4. 排除带"上新/限定/联名"标记的（降低踩雷）。
5. 取第 1 名。

**惊喜款**

1. 排除前两款的主商品。
2. 优先**与懂你款分类不同**的候选。
3. 优先带"上新 / 限定 / 联名"标记的，其次是用户本轮**没有提到**的品类。
4. 同条件下取价格在候选池中位数以上的（"探索"通常意味着没试过的那档）。
5. 取第 1 名；若用户同时选了"想尝鲜"，本款优先级上调。

> 三条规则各自只看**一件事**：懂你看状态、稳妥看结构、惊喜看差异。这样一眼能说清为什么是它。

### 9.4 理由怎么生成（只允许引用三类事实）

| 允许      | 例子                        |
| ------- | ------------------------- |
| 用户本次说的话 | "你说'累了'，挑了单手能吃的汉堡套餐"      |
| 接口给的数据  | "¥26.9，比你的预算低 ¥8.1""本月上新" |
| 实际执行的规则 | "这套是完整套餐，搭配已定，不用再选"       |

**禁止**：心理分析（"你心情不好所以需要安慰"）、营养结论（"高蛋白有助于恢复"）、没数据支撑的形容词（"最健康""最均衡"）。

### 9.5 候选不足 / 数据缺失

| 情况           | 处理                                         |
| ------------ | ------------------------------------------ |
| 硬过滤后 0 个     | 明确说"这个条件下没有可选"，给出最接近的 3 个并标注超出多少，**不静默放宽** |
| 只剩 1–2 个     | 就给 1–2 张卡，说明原因，不硬凑                         |
| 某餐品无价格       | 不进"稳妥款"比较；卡片标"价格待确认"                       |
| D2 无法满足（全同类） | 允许，注明"三者同类，因可选范围有限"                        |
| 营养缺失         | 详情行显示"营养数据暂无"，**不影响推荐**                    |
| 429 / 超时     | 提示稍后再试，不自动重试                               |
| 401 / 403    | 提示检查 Token（手工客户端需 `Bearer` 前缀）             |

### 9.6 随机模式

```python
rng = random.Random(seed)          # seed = int(time*1000)，随结果回传
pool = hard_filter(candidates)      # 预算/忌口/可售
picks = rng.sample(pool, k=...)     # 抽 3 个主商品互异的
```

- 不排序、不调偏好函数（代码路径可审）。
- 抽不满 3 个就去重后重抽，仍不足则返回实际数量。
- seed 回传 → 同一 seed 结果完全一致。

### 9.7 怎么证明输入影响了输出

| 测试 | 方法                         | 通过标准        |
| -- | -------------------------- | ----------- |
| T1 | 固定 seed，只改"状态"（累了 → 想奖励自己） | 懂你款变化       |
| T2 | 固定 seed，只加"不吃牛肉"           | 结果中牛肉类 = 0  |
| T3 | 固定 seed，预算从"不限"改成 ¥25      | 至少 1 款变化    |
| T4 | 同 seed 跑两次                 | 输出完全一致      |
| T5 | 连点 20 次重开（不同 seed）         | 出现 ≥8 种不同组合 |

## 10. 数据来源与能力边界

> 全部业务数据只来自麦当劳官方 MCP（`https://mcp.mcd.cn`）。禁爬虫、禁外部补数、禁编造。

### 10.1 已实测可用


| 能力   | 工具                     | 事实                                                                                | 用途               |
| ---- | ---------------------- | --------------------------------------------------------------------------------- | ---------------- |
| 门店搜索 | `query-nearby-stores`  | `city + keyword` 必须同传（缺一报 `600058`）；返回 storeCode/名称/地址/distance/营业时间；**经纬度恒 0.0** | 选店               |
| 门店菜单 | `query-meals`          | 单店实测 **102 个唯一 code / 14 分类**（3350112，10-21）；`data.meals` 自带 `name` / `currentPrice` / `originalPrice` / `discountType`，`categories[].meals[]` 带 tags；**同一餐品跨分类重复，必须按 code 去重**                            | 候选池              |
| 商品详情 | `query-meal-detail`    | name / image / rounds[].choices[]（isDefault、diffPrice）；**无价格**                    | 名称与组合            |
| 价格   | `calculate-price`      | **单位=分**；支持批量；返回 subtotal / originalSubtotal / discount；**与菜单现价 18/102 不一致**（会员/促销未应用），故展示价取 `currentPrice`，本接口用于改单重算与校验                           | 唯一价格来源           |
| 营养   | `list-nutrition-foods` | 160 条，字段全；**无产品 code，只能按中文名匹配**（抽样 39/46 = 84.8% 命中）                              | **仅详情行**，不参与推荐   |
| 可领券  | `available-coupons`    | 标题 + 领取状态 + 图片；无适用商品/门槛/有效期                                                       | 暂不用              |
| 活动日历 | `campaign-calendar`    | 按日期返回标题+文案+图片，非结构化                                                                | 暂不用（P1 可做"上新"信号） |
| 账号积分 | `query-my-account`     | 正常返回                                                                              | 不用               |
| 订单历史 | `order-list`           | 可调用，结构已知；**当前账号返回空 `data:{}`**                                                    | **不用**（P2 再说）    |

### 10.2 需要进一步验证

| 项                    | 现状                                            |
| -------------------- | --------------------------------------------- |
| 目标门店的品数与分类数          | ✅ 已测：3350112 = **102 个唯一 code / 14 分类**（10-21） |
| 不同门店/城市菜单差异幅度        | 未抽样                                           |
| 早餐时段菜单是否不同           | 未测（当前都是下午/晚间取数）                               |
| `order-list` 有数据时的行为 | 无样本                                           |

### 10.3 当前无法获取（产品必须绕开）

| 缺什么              | 后果              | 处理                 |
| ---------------- | --------------- | ------------------ |
| 营养 ↔ 商品 code 的映射 | 只能按名称对，84.8% 命中 | 详情行能显示就显示，显示不了就说没有 |
| 成分表 / 过敏原 / 交叉接触 | 无法成分级忌口         | 名称排除 + 强制核实提示      |
| 库存 / 售罄          | 无法承诺"现在能拿到"     | 只承诺"在该门店菜单中"       |
| 券的适用范围与门槛        | 算不出券后价          | 不做券相关承诺            |
| 用户画像 / 其他应用行为    | 无法跨应用个性化        | 只用本次输入 + 产品内记录（P1） |
| 销售排行 / 真实热度      | 无法说"大家都在点"      | 只用 tags 里的"人气/上新"  |

### 10.4 必须写进 README 的一句

> **"菜单里有" ≠ "这家店现在一定有"。** `query-meals` 返回该门店当前菜单集合，不含库存与售罄状态；价格与供应以门店实际为准。

### 10.5 工程要求

1. **价格口径（实测得出）**：展示用 `query-meals.currentPrice`（会员/促销后的现价，用户看到的就是它）；`calculate-price.subtotal` 与现价 **18/102 不一致**（多为未应用麦金卡优惠，返回原价），只用它做改单重算与校验。两者都统一 `fen_to_yuan()`、两位小数，不裸展示分值。
2. 菜单/详情/核价结果缓存 `data/cache/<storeCode>.json`，TTL 10 分钟。
3. **调用量（已实测）**：`query-meals` 0.4s 返回 102 个含价格的餐品；批量核价 4 次调用 1.2s 覆盖全部。冷启动不再需要全量详情，实际 ≈6 次调用。
4. 离线快照必须带抓取时间，卡片上显示"快照数据（非实时）"。
5. `query-promotions` **仅企业团餐**（beType=6 / orderType=2），到店场景不可用，V2 不使用。

## 12. 非目标

1. ❌ 不做点餐与支付。
2. ❌ 不做疾病饮食、治疗性饮食建议、营养诊断；不设疾病饮食或恢复期饮食类入口。
3. ❌ 不做减脂、燃脂、增肌、体重管理场景；不设热量上限/蛋白下限求解。
4. ❌ 不做健康评级（"健康分""均衡度"）。
5. ❌ 不爬取任何数据（官网、点评、外卖平台）。
6. ❌ 不读取用户在其他应用的搜索记录或浏览历史；不宣称有此能力。
7. ❌ 不承诺过敏安全。
8. ❌ MVP 不做一周规划、自组组合、外送/得来速。
9. ❌ 不做账号体系与云同步。
10. ❌ 不做社交/排行榜/社区。

## 13. 验收标准（可测、够用、不设统计难题）

| #   | 验收项     | 通过标准                                                   | 怎么测           |
| --- | ------- | ------------------------------------------------------ | ------------- |
| AC1 | 低成本启动   | 入口 A ≤3 次点击出结果；入口 C = 1 次；所有输入可跳过                      | 手动计数          |
| AC2 | 输入影响输出  | 20 组对照（只改状态 / 只改感觉 / 只改预算），≥80% 至少 1 款变化               | 固定 seed 跑对照   |
| AC3 | 三方案真实差异 | 主商品两两不同 = 100%；至少两款分类不同 ≥90%                           | 30 组输入断言      |
| AC4 | 随机真实性   | 20 次重开（不同 seed）→ ≥8 种不同组合；同 seed 结果一致                  | 统计脚本          |
| AC5 | 硬约束     | 预算/排除项违反 = 0（30 组随机用例）                                 | 断言            |
| AC6 | 价格真实可追溯 | 每张卡带 storeCode + 核价时间；抽 5 个餐品与 `calculate-price` 返回值一致 | 人工核对          |
| AC7 | 缺失诚实    | 营养缺失必须显示"暂无"；价格缺失不得进合计比较                               | 抽查 10 张卡      |
| AC8 | 离线可跑    | 断网 + 无 Token，3 个用例全流程跑通，卡片结构与在线一致                      | 断网跑           |
| AC9 | 讲得清     | 60 秒内能说清"它替你少想了几步"，不需要解释算法                             | 找 1 个没听过项目的人试 |

> 不设营养匹配率、减脂达成率这类指标——它们不在本版产品目标里。

## 1. 产品概述

### 1.1 要解决的问题

"中午吃什么、晚上吃什么"是每天发生两次、无法回避、又真实消耗思考能量的任务。叠加健身、预算、生病等额外约束，单次决策成本更高。

现有方案（热量计算器、点餐助手、官方 500 大卡套餐）都停在**单餐**层面：解决"这一顿"。但真实需求是**周期性**的——没有人想连续七天做七次同样的决策。

### 1.2 产品定义

麦麦食历 = **约束求解器 + 一周菜单**。

用户只回答"这周什么状态"，系统基于官方 MCP 数据生成 7 天菜单，满足热量、营养、预算、轮换约束；用户可逐项调换，也可在某天临时切状态。

### 1.3 与官方 500 大卡套餐的关系（重要）

官方 6 个「500 大卡套餐」实测热量 394~476 kcal，证明"热量约束选餐"方向成立。但 6 个固定 SKU 支撑不了一周 14 顿，也不能按预算/蛋白/病号状态调整。

**麦麦食历不造第 7 个 500 大卡套餐，而是把"500 大卡"从一条 SKU 拆成一条约束**，用 125 个售卖单元 + 160 条营养数据重新解出这一周。官方套餐将作为候选池种子之一，保证与官方口径一致。

## 2. 目标用户与场景

| 画像 | 场景故事 |
|---|---|
| 学生（阿莉型） | 健身 + 刷脂 + 生活费有限，每天在食堂和麦当劳之间纠结，想一次排好一周 |
| 上班族 | 午休时间短，只想"照着吃"，不想每天重新选 |
| 任何人生病时 | 发烧 38.5℃，睁不开眼，只想有人直接给出"吃这个" |

**核心用户旅程**：周日晚上花 30 秒选状态 → 得到下周 14 顿 → 每天照着点 → 偶尔换一项 → 周日再生成一次。

## 3. 目标与非目标

### 目标
- 把"一周吃什么"的决策次数从 14 次降到 1 次
- 每餐热量、蛋白、价格可核验、可解释
- 病号场景一键出结果，不额外提问

### 非目标（明确不做）
- ❌ 不做点餐/支付下单（引导用户到官方渠道）
- ❌ 不做医疗/营养诊断（只做客观字段筛选 + 免责声明）
- ❌ 不引入任何非 MCP 数据源（禁止爬虫）
- ❌ 不做社交/排行榜等与决策无关的功能
- ❌ MVP 不做用户登录与云端存储（本地档案文件）

| F3 | 单品调换 / 删减 | P0 | 同价位、同热量、删减，实时重算 |

### 4.2 F1 状态卡与用户档案

**四张状态卡**（共用同一引擎，仅约束不同）：

| 状态 | 约束模板 | 默认参数 |
|---|---|---|
| 日常 | 均衡热量 + 价格带 + 轮换 | 每餐 400~700 kcal，价格≤¥35/餐 |
| 省钱 | 预算上限 | 日均≤¥25，优先套餐/随心配 |
| 燃脂 | 热量缺口 + 蛋白下限 | 每餐 350~550 kcal，蛋白≥20g |
| 病号 | 低油低钠、不冰不辣 | 脂肪≤15g/餐，钠≤800mg/餐，蛋白≥15g |

**用户档案（可选，跳过则用默认值）**：
```json
{
  "budget_per_day": 30,
  "kcal_target_per_meal": 500,
  "protein_min_per_meal": 18,
  "meal_count_per_day": 2,
  "exclusions": ["牛肉"],
  "spicy_ok": true
}
```

### 4.3 F2 一周菜单生成

**输入**：门店（storeCode）+ 状态 + 档案 + 起始日期
**输出**：7 天 × N 餐的菜单结构

**生成流水线**：
```
query-meals(storeCode)                 → 125 个候选 code + 分类
  ↓ 批量 query-meal-detail（缓存）
  ↓ 子项名称归一化 → 匹配营养表 160 条 → 递归累加营养
calculate-price（批量 items）           → 分项价格（分 → 元）
  ↓ 约束过滤（热量/蛋白/脂肪/钠/价格/忌口）
  ↓ 组合优化（贪心 + 随机扰动，保证每次结果不同）
  ↓ 轮换约束（相邻日不同品；同品 ≤2 次/周；分类不连续）
  ↓ 输出菜单 + 三级营养账单 + 周预算
```

**轮换规则（硬约束）**：
- R1 相邻两天不得出现同一菜品
- R2 同一菜品一周出现 ≤2 次
- R3 同一分类（如炸鸡）不得连续两餐出现
- R4 单日两餐热量占比 40%~60%（午餐/晚餐）

### 4.4 F3 单品调换

| 操作 | 规则 | 触发示例 |
|---|---|---|
| 同价位调换 | 价格差 ≤±15%，同类目（主食↔主食、小食↔小食） | "这个换个同价位的" |
| 同热量调换 | 热量差 ≤±10% | "热量差不多但换一个" |
| 删减 | 直接移除该餐，账单同步减少 | "这道不吃" |

**要求**：任何调整后 1 秒内重算当日与整周账单；调整作为偏好信号记录（F9 用）。

### 4.5 F4 病号模式

- 触发：状态卡选"病号"
- 筛选阈值：脂肪 ≤15g、钠 ≤800mg、蛋白 ≥15g、不冰（排除冷饮/冰淇淋）、不辣（排除麦辣系列）
- **交互原则：零提问**——不追问症状，直接给一个套餐 + 一句理由
- 输出「帮我带」卡片（一键复制文本）：
```
【帮我带一份】
麦麦食历病号餐：板烧鸡腿堡 + 小杯玉米杯 + 锡兰红茶
理由：蛋白 25g 好恢复，脂肪 18g 不油腻，热饮不刺激
——来自麦麦食历
```
- **强制免责声明**：营养数据仅供参考，非医疗建议，病中饮食请遵医嘱

### 4.6 F5 营养账单

三级汇总：单餐 → 单日 → 整周（日均热量/蛋白/花费）。
**缺失处理**：营养匹配不到的餐品显示"营养数据暂无"，不参与合计，并在账单标注缺失项数量。

### 4.7 F6 状态临时切换（P1）

- 某天单独切状态 → 仅重算该天
- 切换后仍须满足 R1/R3（与相邻日不重复）

### 4.8 F7 省钱模式（P1，降级实现）

- 主逻辑：预算约束筛选（日均 ≤ 目标）
- 券：读取 `available-coupons`，展示"N 张可领券"，提示"是否可叠加需以下单页核验"
- **降级原因（实测）**：券接口只返回标题+图片，无适用商品/门槛/有效期；`query-store-coupons` 对测试门店返回空数组
- 不做"自动算券后最优价"的承诺，避免误导

## 5. 交互主流程

```
启动 → 选门店（keyword+city）→ 选状态卡 →（可跳过档案）
     → 生成中（≤10s）→ 一周菜单视图
     → 点击任一餐：同价位换 / 同热量换 / 删除
     → 点击某天：切换状态
     → 病号：一键出卡片（复制转发）
     → 导出菜单文本（可截图/分享）
```

**异常流程**：
| 异常 | 表现 |
|---|---|
| 门店搜索失败 | 提示同时填城市与关键词（实测必需） |
| 接口 401/403 | 提示检查 Token（Bearer 前缀） |
| 营养缺失 | 该项标注"营养暂无"，不阻塞生成 |
| 429 限流 | 提示稍候，不自动重试 |

## 6. 数据与接口依赖（基于实测）

| 用途 | 工具 | 实测要点 |
|---|---|---|
| 营养 160 条 | `list-nutrition-foods` | 无 code，按名称匹配；归一化后匹配率 95%+ |
| 菜单 125 品 | `query-meals` | 需 storeCode+orderType=1+beType=1；仅 code+tags |
| 餐品详情 | `query-meal-detail` | 给 name/rounds/choices；无价格 |
| 批量核价 | `calculate-price` | **单位=分**；items 批量返回分项 subtotal |
| 门店 | `query-nearby-stores` | **keyword+city 必须同时传** |
| 可领券 | `available-coupons` | 仅标题+图片 |

**数据流约束**：
- 价格统一 `fen_to_yuan()`，禁止裸展示
- 菜单与详情做会话级缓存（TTL 10 分钟），125 品详情只拉一次
- 单次生成调用量 ≈ 130 次（限流 600/min 的安全区）

## 7. 非功能需求

| 项 | 要求 |
|---|---|
| 生成耗时 | ≤10 秒（缓存命中 ≤2 秒） |
| 限流安全 | 单次生成 ≤150 次调用 |
| 离线能力 | `demo_offline.py` 无 Token 可跑完整流程（内置脱敏样例数据，明确标注"演示数据"） |
| 合规 | 无爬虫、无外部数据；Token 只走环境变量 `YOUR_MCP_TOKEN` |
| 可解释 | 每个餐品都能说明"为什么选它"（热量/蛋白/价格三项依据） |

## 8. 验收标准（AC）

- AC1：给定门店+状态，10 秒内输出 7 天菜单
- AC2：14 餐满足 R1（相邻不重复），违反数=0
- AC3：95%+ 餐品有营养值，缺失项明确标注
- AC4：任一次调换后，当日与整周账单重算正确（误差 0）
- AC5：病号模式所有输出满足脂肪/钠/蛋白阈值
- AC6：无 Token 环境下离线 demo 全流程可跑通
- AC7：README 中的示例与真实输出一致（不写死假数据）

## 9. 风险与降级

| 风险 | 影响 | 降级方案 |
|---|---|---|
| 券规则拿不到 | 省钱模式无法算券后价 | 只做预算筛选 + 券提示 |
| 早餐菜单时段差异未确认 | 早餐覆盖延后 | F8 降 P2 |
| 新品营养缺失（龙焰系列） | 部分餐品无热量 | 标注缺失，不猜 |
| 门店菜单差异 | 不同城市菜品不同 | 全部实时拉取，不硬编码 |
